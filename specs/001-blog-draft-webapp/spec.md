# Feature Specification: ブログ下書き生成 Web アプリケーション

**Feature Branch**: `001-blog-draft-webapp`  
**Created**: 2026-01-11  
**Status**: Draft  
**Input**: User description: "WinUI 3のデスクトップアプリで提供していた「ブログ下書き生成ツール」を、Webアプリとして作り直したい"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ブログ下書きの生成（Priority: P1）

開発者がテックブログの執筆準備として、記事の概要（タイトル案、目的、想定読者、主要な手順や論点の箇条書き）を入力すると、システムは過去の関連記事から文脈を補強し、執筆ガイドに沿った Markdown 形式のブログ下書きを生成して表示する。生成された下書きはコピー可能で、そのままエディタに持ち込める。

**Why this priority**: コア機能であり、これが無ければツールの存在価値がない。既存のデスクトップ版で最も使われている機能を Web で提供することで、場所を問わず利用可能になる。

**Independent Test**: ユーザーが概要（例: 「Azure Functions で Durable Functions を使った非同期処理」）を入力フォームに記入して「生成」ボタンを押すと、Markdown 形式の下書きが画面に表示され、コピーボタンでクリップボードにコピーできる。

**Acceptance Scenarios**:

1. **Given** ユーザーがログインしておらず初回アクセス時、**When** ブログ記事の概要（タイトル案、目的、主要な手順）を入力して「下書きを生成」ボタンを押す、**Then** 設定されたタイムアウト時間内に Markdown 形式の下書きが画面に表示され、コピー可能な状態になっている
2. **Given** RAG（検索サービス）が有効で関連記事が存在する状態、**When** 概要を入力して生成を実行、**Then** 過去記事の関連情報が下書きに反映され、出典やコンテキストが適切に組み込まれている
3. **Given** 生成中にタイムアウトが発生した場合、**When** 設定されたタイムアウト時間（例: 120秒）を超過、**Then** エラーメッセージ「生成に時間がかかりすぎています。もう一度お試しください」が表示され、再試行が可能である
4. **Given** 生成が完了して下書きが表示されている状態、**When** ユーザーが「コピー」ボタンをクリック、**Then** Markdown 全文がクリップボードにコピーされ、「コピーしました」という確認メッセージが表示される

---

### User Story 2 - LLM 入力内容のプレビュー（デバッグモード）（Priority: P2）

開発者が生成品質を改善したい場合、または文体カード・RAG 結果が期待通りかを確認したい場合、「プレビューモード」を選択すると、LLM に実際に送信される予定のプロンプト全文（システムプロンプト + RAG コンテキスト + ユーザー概要）を LLM に送信せずに画面に表示する。

**Why this priority**: 生成品質のトラブルシューティングやチューニングに不可欠。ただし、メイン機能（下書き生成）が動作すれば価値提供は可能なため、P2 とする。

**Independent Test**: ユーザーが「プレビューモード」を有効にして概要を入力し、「プレビュー」ボタンを押すと、LLM 推論は行わず、送信予定のプロンプトテキスト全文が画面に表示される。

**Acceptance Scenarios**:

1. **Given** ユーザーが「プレビューモード」を選択した状態、**When** 概要を入力して「プレビュー」ボタンを押す、**Then** LLM に送信される予定のプロンプト全文（システムプロンプト、RAG コンテキスト、ユーザー概要）が整形されて画面に表示され、LLM API は呼び出されない
2. **Given** プレビューモードで表示された内容、**When** ユーザーが「コピー」ボタンをクリック、**Then** プロンプト全文がクリップボードにコピーされる
3. **Given** プレビューモードが有効、**When** RAG が無効化されている場合、**Then** プロンプトには RAG コンテキストが含まれず、その旨の注記が表示される

**[必須] プレビューモードで画面に表示されるプロンプト内容（システムプロンプト、RAGコンテキスト、ユーザー概要）は、ログや外部出力に一切記録してはならない。**
※プレビューモードで画面に表示される内容（プロンプト全文）は、ログや外部出力に一切記録してはならない（必須）。

---

### User Story 3 - 設定の管理（Priority: P3 - 管理者向け）

**スコープ**: Web アプリのユーザーが直接操作する設定画面は不要。Web アプリ管理者が、アプリケーション設定（appsettings.json、環境変数、Azure App Configuration 等）または シークレットストア（Azure Key Vault 等）を通じて、LLM や RAG の設定を管理する。

**Why this priority**: 運用環境における柔軟な設定変更を可能にするため。ただし、ユーザー向け UI では なく、管理者向けのインフラ設定として扱う。

**Independent Test**: 管理者が Azure ポータルから LLM モデル ID やタイムアウト時間を変更し、Web アプリを再起動（または ホットリロード）すると、次回のリクエストから新しい設定が適用される。

**Acceptance Scenarios**:

1. **Given** Web アプリ管理者が環境変数またはシークレットストアで LLM モデル ID、最大トークン数、タイムアウト時間を更新した場合、**When** Web アプリを再起動し、ユーザーが下書き生成を実行、**Then** 新しい設定が適用され、生成が実行される
2. **Given** 管理者が RAG を無効化する設定（Enabled=false）を適用、**When** Web アプリが再起動され、ユーザーが下書き生成を実行、**Then** 過去記事の検索は行われず、ユーザー概要と文体カードのみで下書きが生成される
3. **Given** Web アプリ起動時に設定（API キー、スコア閾値など）の値が不正または未設定の場合、**When** Web アプリが起動しようとする、**Then** 起動時にエラーログを出力し、管理者に通知する

---

### Edge Cases

- **RAG 検索が失敗した場合**: システムは RAG コンテキストなしで生成を継続し、警告メッセージ「関連記事の検索に失敗しました。過去記事の参照なしで生成します」を表示する
- **LLM API キーが未設定または無効な場合**: 生成ボタンを押した時点でエラーメッセージ「LLM API の設定が不正です。設定画面で API キーを確認してください」を表示し、生成は行わない
- **文体カード読み込み失敗**: アプリケーション起動に失敗し、エラーログを出力する（フォールバックは行わない、フェイルファースト）
- **入力が空の場合**: 「下書きを生成」ボタンは無効化される（ユーザーはクリック不可）
- **生成結果が異常に短い場合（例: 100文字未満）**: 警告メッセージ「生成結果が短すぎます。入力内容を詳しくするか、設定を確認してください」を表示する
- **複数のユーザーが同時にアクセスした場合**: 各リクエストは独立して処理され、他のユーザーの生成処理に影響を与えない
- **タイムアウトが 0 または未設定の場合**: デフォルトで 120 秒のタイムアウトを適用する（Web アプリ起動時の設定で判定）
- **プレビューモードで機微情報が含まれる場合**: プレビュー結果の表示前に警告メッセージ「この内容には機密情報が含まれる可能性があります。画面のスクリーンショットや共有にご注意ください」を表示する
- **Web アプリ起動時に設定値が不正な場合（例: 文体カード未設定、API キー未設定、RAG エンドポイント無効）**: エラーログを出力し、アプリケーションの起動に失敗する。ユーザー向けの画面には「システムが正しく構成されていません。管理者に連絡してください」というメッセージを表示する

## Requirements *(mandatory)*

### Functional Requirements

#### コア機能（生成）

- **FR-001**: システムは、ユーザーが入力したブログ記事の概要（タイトル案、目的、想定読者、手順の箇条書きなど）を受け取り、Markdown 形式のブログ下書きを生成して表示しなければならない
- **FR-002**: システムは、生成された下書きをクリップボードにコピーする機能を提供しなければならない
- **FR-003**: システムは、RAG（Azure AI Search）を使用して過去記事から関連情報を検索し、生成プロンプトに含めなければならない
- **FR-004**: システムは、固定の「文体カード」（執筆ガイド）をシステムプロンプトとして LLM に送信しなければならない
- **FR-005**: システムは、LLM API（Chat Completions 互換）を呼び出してブログ下書きを生成しなければならない
- **FR-006**: システムは、生成が設定されたタイムアウト時間（デフォルト: 120秒）を超過した場合、処理を中断してエラーメッセージを表示しなければならない

#### デバッグ機能（プレビューモード）

- **FR-007**: システムは、「プレビューモード」が有効な場合、LLM に送信される予定のプロンプト全文（システムプロンプト + RAG コンテキスト + ユーザー概要）を画面に表示し、LLM API は呼び出さないようにしなければならない
- **FR-008**: プレビューモードで表示されるプロンプトは、実際の生成時と完全に同一の内容でなければならない
- **FR-009**: プレビューモードでは、表示されたプロンプトをコピー可能にしなければならない

#### RAG（検索機能）

- **FR-010**: システムは、RAG が有効な場合、ユーザー入力をクエリとして Azure AI Search のベクトル検索を実行し、Top-K 件の関連チャンクを取得しなければならない
- **FR-011**: システムは、取得した RAG チャンクを整形（重複除去、長さ制限、出典情報の付与など）してプロンプトに追加しなければならない
- **FR-012**: システムは、RAG 検索が失敗した場合でも、RAG コンテキストなしで生成を継続しなければならない（警告メッセージを表示）
- **FR-013**: システムは、RAG のスコア閾値（MinimumScore）を下回るチャンクを除外しなければならない

#### 設定管理

- **FR-014**: システムは、起動時にアプリケーション設定（appsettings.json、環境変数、Azure App Configuration 等）から LLM API キー、モデル ID、最大トークン数、タイムアウト時間などの設定項目を読み込まなければならない
- **FR-015**: システムは、起動時にアプリケーション設定から RAG の有効/無効、検索エンドポイント、インデックス名、Top-K、スコア閾値などの設定項目を読み込まなければならない
- **FR-016**: システムは、文体カードの内容を秘匿情報として扱い、リポジトリや配布物に含めてはならない。シークレットストア（Azure Key Vault 等）または設定ファイルから起動時に読み込まなければならない。読み込みに失敗した場合、フェイルファースト（起動失敗）とする
- **FR-017**: システムは、起動時に必須の設定項目（LLM API キー、RAG エンドポイント、文体カードなど）が未設定または不正な場合、エラーログを出力し、Web アプリの起動に失敗しなければならない
- **FR-018**: システムは、ユーザーが操作可能な設定画面を提供してはならない。すべての設定管理は Web アプリ管理者によるインフラ層での構成に限定する

#### セキュリティ

- **FR-019**: システムは、LLM API キー、RAG API キーなどの秘匿情報をブラウザに送信してはならない（すべてサーバ側で保持し、アプリケーション起動時のみメモリに読み込む）
- **FR-020**: システムは、ユーザー入力、RAG チャンク、生成結果、プロンプト全文を含むリクエスト/レスポンスをログに記録してはならない。デバッグ・本番環境に関わらず、これらの機微情報は記録禁止とする（ただし、構造化ログで request ID など最小限の追跡情報は記録可）
- **FR-021**: システムは、プレビューモードで表示される内容に機微情報が含まれる可能性があることを警告しなければならない
- **FR-022**: システムは、設定値（API キー、エンドポイント URL、秘密情報）をコード内に埋め込んではならず、すべてを環境変数、設定ファイル、またはシークレットストアから読み込まなければならない

#### エラーハンドリング

- **FR-023**: システムは、LLM API 呼び出しが失敗した場合、エラーの種類（認証エラー、タイムアウト、レート制限、サービスエラーなど）を判別し、ユーザーに適切なエラーメッセージを表示しなければならない
- **FR-024**: システムは、再試行可能なエラー（タイムアウト、一時的なサービスエラー）の場合、「再試行」ボタンを表示しなければならない
- **FR-025**: システムは、起動時に設定不備（API キー未設定など）が検出された場合、エラーログを出力し、管理者に通知しなければならない。ユーザーには「システムが正しく構成されていません。管理者に連絡してください」というメッセージを表示する

#### 非機能要件

- **NFR-001**: システムは、サーバ側処理（RAG 検索 + LLM 生成）を 120 秒以内に完了しなければならない（タイムアウト設定可能）
- **NFR-002**: システムは、単一の管理者（C# 技術者 1 名）が設定変更、ログ確認、トラブルシューティングを行える設計でなければならない
- **NFR-003**: システムは、運用中のエラーや警告を構造化ログとして出力し、トレーサビリティを確保しなければならない
- **NFR-004**: システムは、複数の環境（開発、本番）で設定を切り替え可能でなければならない（環境変数または設定ファイルで管理）
- **NFR-005**: システムは、Azure AI Search と LLM API の外部依存に対する障害を想定し、片方が失敗しても他方に影響を与えない設計でなければならない
#### テスト要件(Testing Requirements)

- **TR-001**: すべての UI コンポーネント(Blazor ページ、フォーム、ボタン、状態管理ロジック)は、bUnit によるユニットテストでカバーしなければならない
- **TR-002**: すべての API エンドポイントは、統合テスト(WebApplicationFactory 使用)でカバーしなければならない
- **TR-003**: すべてのコアビジネスロジック(PromptComposer, RetrievalService, LlmClient など)は、NUnit + Moq によるユニットテストでカバーしなければならない
- **TR-004**: すべての主要ユーザーフロー(入力 → 生成 → 結果表示、プレビューモード、エラー処理)は、Playwright による E2E テストでカバーしなければならない
- **TR-005**: テストは、外部依存(Azure AI Search、LLM API)をモック化し、実 OS 環境(レジストリ、サービス、ドライバ等)を変更してはならない
- **TR-006**: すべてのテストは、NUnit の Assert.That 形式で記述しなければならない
- **TR-007**: UI コンポーネントテストでは、JavaScript インターロップ(IJSRuntime)、HTTP クライアント(IHttpClientFactory)、ナビゲーション(NavigationManager)をモック化しなければならない
- **TR-008**: E2E テストでは、ブラウザ操作の実際の動作(入力、クリック、表示確認、クリップボードコピー)を検証しなければならない
- **TR-009**: テストカバレッジは、行カバレッジ 80% 以上、分岐カバレッジ 70% 以上を維持しなければならない
- **TR-010**: 新機能追加時は、機能実装と同時に対応するテスト(ユニット、統合、E2E)を作成しなければならない
### Key Entities

- **ブログ概要（BlogOverview）**: ユーザーが入力する記事の概要情報。タイトル案、目的、想定読者、主要な手順や論点の箇条書きを含む自由テキスト。
- **文体カード（StyleCard）**: LLM に送信する固定のシステムプロンプト。執筆方針、トーン、構成テンプレート、出力ルールなどを定義。秘匿情報として扱われる。
- **RAG チャンク（RAGChunk）**: Azure AI Search から取得される過去記事の断片。本文フィールド、スコア、出典情報（記事URL、タイトルなど）を含む。
- **プロンプト（Prompt）**: LLM に送信される入力の集合体。システムプロンプト（文体カード）、RAG コンテキスト（整形済みチャンク）、ユーザー概要の 3 要素で構成される。
- **下書き（Draft）**: LLM が生成した Markdown 形式のブログ記事本文。Mermaid 図やコードブロックを含む場合がある。
- **設定（Configuration）**: LLM API キー、モデル ID、タイムアウト、RAG エンドポイント、インデックス名、Top-K、スコア閾値などのシステム設定項目。環境ごとに管理される。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ユーザーが記事の概要を入力してから下書きが画面に表示されるまでの時間が 90% のケースで、設定されたタイムアウト時間（デフォルト: 120秒）以内である
- **SC-002**: 生成された下書きが、ユーザーの概要入力に対して関連性が高く、そのままエディタで編集可能な品質である（主観評価: 5回の生成で 4回以上が「そのまま使える」と評価される）
- **SC-003**: プレビューモードで表示されるプロンプトが、実際の生成時と 100% 一致している（自動テストで検証可能）
- **SC-004**: RAG 検索が失敗した場合でも、生成処理が継続され、下書きが出力される（フォールバック成功率 100%）
- **SC-005**: 起動時に設定不備が検出された場合、エラーログが記録され、管理者が 5 分以内に問題の原因を特定し、設定を修正できる（トレーサビリティの確保）
- **SC-006**: 複数ユーザーが同時にアクセスした場合でも、各リクエストが独立して処理され、レスポンス時間が単一ユーザー時と比較して 20% 以内の増加に収まる（同時接続 10 ユーザーまで）
- **SC-007**: アプリケーション起動から最初の生成完了までの時間が 5 分以内である（初回設定を含む）
- **SC-008**: ログに記録されるエラー情報から、管理者が 15 分以内に問題の原因を特定できる（トラブルシューティング時間の短縮）- **SC-009**: すべての UI コンポーネント、API エンドポイント、コアビジネスロジックが、自動テストによって検証されている(テストカバレッジ: 行カバレッジ 80% 以上、分岐カバレッジ 70% 以上)
- **SC-010**: すべての主要ユーザーフロー(入力 → 生成、プレビュー、エラー処理、リトライ)が、Playwright E2E テストで自動検証されている(最低 10 シナリオ以上)
- **SC-011**: CI パイプラインでテストが自動実行され、テスト失敗時はビルドが失敗する(回帰検出率 100%)
- **SC-012**: 新機能追加時、対応するテスト(ユニット、統合、E2E)が同時に実装され、テストカバレッジが低下しない

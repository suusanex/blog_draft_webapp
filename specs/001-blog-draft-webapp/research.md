# Research: ブログ下書き生成 Web アプリケーション

**Branch**: `001-blog-draft-webapp` | **Date**: 2026-01-11  
**Purpose**: Phase 0 - 技術選定と設計方針の調査

## Overview

WinUI 3 デスクトップアプリから Blazor Web App への移植に際し、技術スタック、RAG 整形戦略、タイムアウト/リトライ設計、秘匿情報管理などの判断材料を調査・文書化する。

---

## 1. Blazor Interactive Server vs WebAssembly の選定

### Decision: Interactive Server を採用

### Rationale

1. **秘匿情報の保護**: LLM API キー、RAG API キー、文体カードをブラウザに送信しない。すべてサーバ側で保持できる。
2. **単純なデプロイ**: 単一ホスト（Azure App Service 等）で Blazor UI + API を統合管理。WASM の場合は API を別途ホストする必要がある。
3. **リアルタイム性**: 将来的にストリーミング生成（Server-Sent Events）を追加する場合、SignalR の低レイテンシが有利。
4. **開発効率**: 1 人運用のため、フロントエンド・バックエンドの分離よりも、C# で統一したコードベースの保守性を優先。

### Alternatives Considered

- **Blazor WebAssembly + 別途 API**: セキュリティは確保できるが、デプロイと運用の複雑さが増す。個人運用には過剰。
- **ASP.NET Core MVC / Razor Pages**: Blazor の双方向バインディングと UI コンポーネントの再利用性が劣る。

## 2. API 設計: Minimal API vs Controllers

### Decision: Minimal API を採用（初期）、Controller への移行パスを確保

### Rationale

1. **保守性重視**: エンドポイント数が少ない（`/draft`, `/draft/preview`, `/health`）ため、Minimal API のシンプルさが有効。
2. **型安全性**: ASP.NET Core 7+ の Minimal API は、リクエスト/レスポンスモデルをバインディングでき、Controller と同等の型安全性を持つ。
3. **移行容易性**: 将来的にエンドポイントが増えた場合、Controller に移行するコストは低い（同一の DI コンテナと OpenAPI 対応）。

### Alternatives Considered

- **Controllers**: エンドポイント数が 10 以上になる場合は Controllers の方が構造化しやすいが、初期段階では過剰。

## 3. RAG 整形ルール

### Decision: 以下のルールで Azure AI Search の結果を整形

1. **Top-K 制限**: デフォルト 5 件（設定可能）。
2. **スコア閾値**: MinimumScore（例: 0.7）を下回るチャンクを除外。
3. **最大文字数**: 各チャンク 500 文字まで（超過分は切り捨て + "..." 付与）。
4. **重複除去**: 同一記事から複数チャンクが返された場合、最初の 1 件のみ採用。
5. **出典情報付与**: 各チャンクに記事タイトルと URL を Markdown リンク形式で追加（例: `[記事タイトル](URL)`）。
6. **プロンプト埋め込み**: 整形後のチャンクを以下の形式でプロンプトに追加:
   ```
   ## 過去記事からの関連情報（参考）
   
   1. [記事タイトル](URL)
      > (チャンク本文)
   
   2. [記事タイトル](URL)
      > (チャンク本文)

- **ノイズ削減**: 長すぎるチャンクや低スコアチャンクは、LLM の文脈理解を阻害する。
- **トークン節約**: 文体カード（1000-2000 トークン）と新規概要（500 トークン想定）で既に文脈を消費するため、RAG チャンクは最小限に抑える。

## 8. RAG 失敗時のハンドリング

### Decision: RAG 失敗時は `RAG_ERROR` を返し、生成処理を中断

### Failure Behavior

1. **RAG 検索失敗**: Azure AI Search がタイムアウト、認証エラー、503 などを返した場合は `AzureAISearchService` が例外を `RagException` として再スローし、GlobalErrorHandler はステータス 500（`RAG_ERROR`、IsRetryable=true）の `ErrorResponse` を生成する。
    - UI は「関連記事の検索に失敗しました」というメッセージを表示し、再試行ボタンを有効化する。処理はここで終了し、生成は続行しない。
    - RAG を意図的に無効化（設定値 `AzureAISearch:Enabled=false`）した場合は例外ではなく空のチャンクで継続するが、今回の失敗とは区別される。

2. **Top-K ゼロ件**: スコア閾値により全てのチャンクが除外されても、検索自体は成功しているため生成は継続するが、ログには「RAG チャンクが見つかりませんでした」と情報レベルで残す。

### Rationale

- **品質担保**: RAG に誤ったデータが含まれている可能性があるため、失敗時に生成を止めて再実行を促すことで、生成結果の信頼性を維持する。
- **運用監視**: `RAG_ERROR` を返すことで管理者がアラートやリトライループを検知できるようにし、問題の原因調査を容易にする。
- **Constitution 遵守**: 異常時はフェイルファーストとし、ユーザーに再試行を求める設計方針と整合する。

### Alternatives Considered

- **警告＋フォールバック**: メッセージを表示して生成を継続する案も検討したが、RAG に依存するコンテキストが欠如した下書きは誤解を招くため棄却。
- **キャッシュした結果の再利用**: 過去の RAG 結果を再送するアプローチは、初期実装では複雑すぎるため見送った。
- **重複除去なし**: 同一記事から複数チャンクを取得すると、冗長性が高まりトークンを浪費。
- **出典情報なし**: デバッグ時に RAG チャンクの品質を検証できない。

## 4. LLM タイムアウトとリトライ戦略

### Decision: 固定タイムアウト（デフォルト 600 秒）、リトライは手動のみ

### Rationale

1. **Web 制約**: Azure App Service のデフォルトタイムアウト（230 秒）はフロントのリクエスト向けだが、LLM 呼び出し自体はサーバー内で完結するため、600 秒まで許容して長時間処理に対応する。
2. **ユーザー体験**: 600 秒近い生成でも UI 上で進行中のフィードバックと再試行ボタンを用意し、ユーザーが発生タイミングを判断できるようにする。
3. **コスト抑制**: 自動リトライは、LLM API コストの予期しない増加を招く（特に reasoning モデルの場合）。

### Timeout Configuration

- 設定項目: `OpenAI:RequestTimeoutSeconds`（デフォルト 600）
- 0 または未設定の場合は、600 秒を適用（"無制限" は採用しない）。

### Retry Policy

- **自動リトライなし**: LLM API の失敗（タイムアウト、レート制限、5xx エラー）時は、エラーメッセージを表示し、ユーザーが「再試行」ボタンをクリックして再実行。
- **将来拡張**: ジョブキュー（Azure Storage Queue 等）を導入する場合、バックグラウンドでリトライ可能。ただし初期段階では不要。

### Alternatives Considered

- **自動リトライ（Polly 等）**: コスト増加とタイムアウトの累積（例: 3 回リトライで 360 秒）がリスク。
- **無制限タイムアウト**: Azure App Service の制約に抵触する。

## 5. 秘匿情報管理（Secret Store）

### Decision: 開発と運用で異なるストレージを使用

#### 開発環境

- **User Secrets** (`dotnet user-secrets`): ローカル開発時に API キー、エンドポイント URL、文体カードを保存。
- パス例: `%APPDATA%\Microsoft\UserSecrets\<user_secrets_id>\secrets.json`

#### 運用環境

- **Azure Key Vault**: API キー、RAG API キー、文体カードを保存。
- `Azure.Extensions.AspNetCore.Configuration.Secrets` パッケージで起動時に読み込む。

### Configuration Loading Priority

1. User Secrets（開発環境のみ）
2. 環境変数（Azure App Service の Application Settings）
3. Key Vault（運用環境）
4. appsettings.json（デフォルト値、秘匿情報は含まない）

### Rationale

- **リポジトリからの分離**: 秘匿情報をコミットしない。
- **環境差分の吸収**: 開発・本番で異なる API キーや文体カードを使い分け可能。
- **監査**: Key Vault のアクセスログで、誰がいつ秘匿情報にアクセスしたかを追跡できる。

### Alternatives Considered

- **appsettings.json に直接記載**: セキュリティリスクが高い（誤コミットの可能性）。
- **環境変数のみ**: 文体カードのような長文は環境変数に不向き（文字数制限、改行の扱い）。

## 6. ログ戦略（秘匿情報の扱い）

### Decision: 本番環境ではユーザー入力・RAG チャンク・プロンプトをログに記録しない

### Log Levels

- **Debug**: 開発環境のみ有効。プロンプト全文、RAG チャンク全文を記録。
- **Information**: リクエスト ID、エンドポイント、実行時間、RAG ヒット件数、LLM モデル名を記録。
- **Warning**: RAG 検索失敗、スコア閾値による除外、タイムアウト警告を記録。
- **Error**: 例外（`Exception.ToString()`）、スタックトレース、リクエスト ID を記録。

### Sensitive Data Redaction

- **API キー**: ログに記録しない（`ILogger` の設定で除外）。
- **ユーザー入力**: 本番環境では記録しない。デバッグ時は最初の 100 文字のみ。
- **プロンプト全文**: デバッグ時のみ記録。本番環境では "Prompt sent to LLM" のみ。
- **文体カード**: ログに記録しない（機微情報）。

### Rationale

- **ガバナンス遵守**: Constitution の「秘匿情報はログに出力しない」要件を満たす。
- **トラブルシューティング**: リクエスト ID でログを追跡し、エラー発生箇所を特定できる。
- **プライバシー**: ユーザー入力に機微情報が含まれる可能性を考慮。

### Alternatives Considered

- **全ログ記録**: プライバシーリスクが高い。
- **ログ記録なし**: トラブルシューティングが困難。

## 7. プレビューモード（LLM 入力表示）の境界設計

### Decision: プレビューモードでは、文体カードを含む完全なプロンプトを表示

### Display Content

プレビューモードで表示される内容:
1. **システムプロンプト**: 文体カード全文（機微情報）。
2. **RAG コンテキスト**: 整形済みチャンク（出典情報含む）。
3. **ユーザー概要**: 入力された新規記事の概要。

### Security Measures

- **警告メッセージ**: プレビュー結果の表示前に「この内容には機密情報が含まれる可能性があります。画面のスクリーンショットや共有にご注意ください」と表示。
- **ログ記録禁止**: プレビューモードで表示された内容は、ログに一切記録しない（仕様で明示）。
- **認証**: 将来的に複数ユーザーで運用する場合、プレビューモードへのアクセスを管理者権限に制限（初期段階では不要）。

### Rationale

- **デバッグ価値**: 文体カードを含めないと、生成品質のトラブルシューティングができない。
- **リスク管理**: 表示内容の機微性を警告し、ユーザーの注意を喚起。

### Alternatives Considered

- **文体カード除外**: デバッグ価値が半減。文体カードの不備が原因の場合、問題を特定できない。
- **マスキング**: 文体カードの一部をマスクする案もあるが、実装コストに見合わない。

## 9. テスト戦略

### Unit Test

- **対象**: PromptComposer、RAG 整形ロジック、設定バリデーション。
- **ツール**: NUnit + Moq（Assert.That 形式）。
- **方針**: 外部 API（Azure AI Search、LLM）をモック化し、ロジックのみをテスト。

### Integration Test

- **対象**: API エンドポイント（`/draft`, `/draft/preview`）。
- **ツール**: WebApplicationFactory + NUnit。
- **方針**: 外部 API をスタブ化（テスト用の ILlmClient、IRetrievalService 実装を DI）。実 OS 環境は変更しない。

### Manual Test

- **対象**: 実際の Azure AI Search、OpenAI API を使った End-to-End テスト。
- **タイミング**: 開発環境で実施。CI では実行しない（秘匿情報を CI 環境に持ち込まない）。

### Rationale

- **Constitution 遵守**: UnitTest と IntegrationTest は実 OS 環境を変更しない。
- **コスト抑制**: CI で実 LLM API を叩かない（API コストの増加を防ぐ）。
- **再現性**: モック/スタブにより、外部依存に影響されないテストを実現。

## 10. 将来拡張ポイント（初期実装には含まない）

### Job Queue（非同期生成）

- **目的**: タイムアウト時間を超える長時間生成（例: 複雑な reasoning モデル）に対応。
- **技術**: Azure Storage Queue + Background Service。
- **API 設計**: `POST /draft-jobs` → `GET /draft-jobs/{id}`（ポーリング）。

### ストリーミング生成

- **目的**: LLM の生成途中結果をリアルタイム表示。
- **技術**: Server-Sent Events または SignalR。
- **メリット**: ユーザー体験向上（待機時間の体感削減）。

### 複数文体カード

- **目的**: プロジェクトごと、読者層ごとに異なる文体カードを切り替え。
- **設計**: 文体カードを DB またはファイルシステムで管理し、UI で選択可能にする。

### 生成履歴の保存

- **目的**: 過去の生成結果（入力・RAG・出力）をセットで保存し、品質改善の材料にする。
- **ストレージ**: Azure Cosmos DB または Blob Storage。

## Summary

| 項目 | 選定結果 | 主な理由 |
|------|----------|----------|
| UI 技術 | Blazor Interactive Server | 秘匿情報保護、シンプルなデプロイ |
| API 設計 | Minimal API | エンドポイント数が少ない、移行容易 |
| RAG 整形 | Top-K 制限、スコア閾値、重複除外、出典付与 | トークン節約、トレーサビリティ |
| タイムアウト | 固定 600 秒、リトライなし | Web 制約、コスト抑制 |
| 秘匿情報管理 | User Secrets（開発）、Key Vault（運用） | リポジトリ分離、環境差分吸収 |
| ログ戦略 | 本番環境で機微情報を記録しない | ガバナンス遵守、トラブルシューティング両立 |
| プレビューモード | 文体カード含む完全なプロンプトを表示 | デバッグ価値、警告で安全性確保 |
| RAG 失敗時のエラー | 失敗時は `RAG_ERROR` を返してフェイルファースト | 管理者が異常を検知しやすく、誤った下書きを防げる |
| テスト戦略 | UnitTest + IntegrationTest（モック化） | 再現性、コスト抑制、Constitution 遵守 |

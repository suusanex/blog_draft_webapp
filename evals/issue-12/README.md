# Issue #12 評価コーパス

下書き生成が「入力の内容と論理展開を保ち、不要な解説を増やさない」かを見るための材料。

成功条件は文字数や見出し数の削減ではない。必要な説明や入力の具体例を削って短くした結果も不合格とする。

## このディレクトリ

- `inputs/` — Issue #12 で提示された 4 例の評価入力。技術記述の正誤は未検証であり、完成記事から逆算したメモではない。
- `keep-drop.md` — 各例で残すべき意味・論理・参照と、追加してほしくない周辺説明。
- `baseline/` — 変更前の実生成結果を置く場所。未実施なら空のままにする。

## 自動テストとの関係

ユニット／統合テストは、検索を呼ばないこと、旧 RAG スナップショットを送らないこと、短いアウトラインを拒否しないこと、元入力が本文生成へ渡ること、プレビューと実生成の入力が一致することを保証する。

それらの通過は、実モデルが Goal Context を満たした証拠にはならない。

## 実モデル評価（人手）

同じモデル・設定・入力で、一括生成（`/draft`）とワークフロー（アウトライン確定 → 本文）の両方を見る。

見るもの:

- 入力の意味の欠落
- 論理関係・確度の変質（未確認を確定、経験の創作）
- 必要な説明の不足
- 不要な一般説明の追加
- URL・コマンド・数値・条件の保持

文字数と見出し数は観察値に留める。URL の文字列一致だけで意味の保持を保証したとしない。

実施できない場合は、プロンプトやスタブの検証とは区別して未検証と報告する。変更前後の実データ比較は手動受入作業とし、自動実行には含めない。

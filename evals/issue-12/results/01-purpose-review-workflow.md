# 目的レビューで実装のゴール逸脱を減らす

ゴールを書いたドキュメントや Issue をもとに、AI へプランから実装まで任せる場面では、完成した実装が当初のゴールを満たしていないことがある。この問題を減らすため、PR 作成後に「目的レビュー」を行っている。

ここでいう目的レビューは、仕様への形式的な準拠だけでなく、実装が当初のゴールを実現しているかを確認するレビューを指す。多くのコーディング場面で使える方法だと考えている。

## 別の AI にゴールと PR だけを渡す

PR を作成したら、別の AI にゴール文書と PR の URL を渡し、次のように依頼する。

> この PR が目的を満たしているかレビューして

レビューを担当させるのは、実装の経過を知っているコーディングエージェント自身ではなく、別のエージェントだ。入力もゴールと PR だけに絞る。

### 途中の誤解からレビューを切り離す

別のエージェントに限定した情報だけを渡すのは、実装途中で積み重なった誤解にレビューが引きずられにくくするためだ。仕様書には従っていても、当初のゴールを実現していないパターンを検出したい。

## AI に起きやすい「目的を見失った膨張」

最近の AI は、指示とまったく違う行動や、ハルシネーションによる暴走が減ったと感じる。一方で、直前の AI の判断を根拠に次の設計を重ね、当初の目的から離れていくことがある。

普通のオーバーエンジニアリングを「早すぎた作り込み」という時間軸で捉えるのに対し、AI では「目的を見失った膨張」が多いように思う。

### 自己復旧へ膨張する例

たとえば、当初のゴールが「可用性は最小限でよく、異常時はエラーを報告して止まる」だったとする。それが実装中の判断によって、次のように膨張する。

1. 機能 A を追加する
2. ベストプラクティスとして自動復旧を追加する
3. 復旧できない場合のフェイルセーフを追加する

Goal Context に「自己復旧を増やさず停止する」と書かれていれば、過剰な自己復旧の実装が目的レビューで指摘される可能性を期待できる。

## 手動レビューの実績と限界

この目的レビューは手動で依頼しても効果がある。自分の経験では、レビューを通過したものは、たいていそのまま疎通している。

ただし、これは自分が試した範囲での観察であり、一般的な品質保証ではない。

## 最大 3 回繰り返す自動レビュー

手動でも使えるが、毎回レビューを依頼し、指摘を修正して再度レビューするのは手間がかかる。そこで、専用 Skill とゴール文書を指定すると、目的レビューと指摘修正を最大 3 回まで繰り返す自動版を用意した。

「最大 3 回」は一般的な推奨回数ではなく、ここで紹介する自動レビューの動作上の性質である。

### 事前準備

まず、レビュー用エージェントを持つアプリをインストールする。

https://github.com/suusanex/coding_agent_plan_and_verify_process/blob/main/apps/PurposeReviewRunner/README.md

次に、専用 Skill を apm などで導入する。

https://github.com/suusanex/coding_agent_plan_and_verify_process/blob/main/apm-packages/persistent-purpose-review/README.md

### 実行時の操作

実行時は、Skill とレビューのコンテキストを指定する。たとえば、Issue をゴール文書としてそのまま渡す場合は、次のように依頼する。

> SKILL persistent-purpose-review を実行して。レビューのコンテキストは issue https://github.com/suusanex/blog_draft_webapp/issues/3 をそのまま渡して

### 導入負担についての留保

アプリと Skill の事前準備が必要なため、単純に「指定するだけ」と言うには導入が面倒だ。一方で、準備後は毎回手動でレビュー依頼と指摘修正を繰り返すより楽になる。

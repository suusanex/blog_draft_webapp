# 別の AI にゴールと PR だけを渡して目的レビューする

ゴールを書いたドキュメントや Issue をもとに、AI へプラン作成から実装まで任せる場面では、実装が当初のゴールを満たしていないことがある。この問題をレビューで減らすため、PR 作成後に別の AI を使って目的レビューをしている。多くのコーディング場面で使える方法だと思う。

## 経過を知らない別の AI にレビューさせる

PR を作成したら、別の AI にゴール文書と PR の URL を渡し、「この PR が目的を満たしているかレビューして」と依頼する。

実装までの経過を知っているコーディングエージェント自身ではなく、別のエージェントにゴールと PR だけを見せるのがポイントだ。途中で生じた誤解に引きずられにくくなり、仕様書には従っていても当初のゴールを実現していないパターンを検出しやすくなる。

実績として、このレビューを通過したものは、たいていそのまま疎通する。ただし、これは一般的な保証ではない。

## AI では「目的を見失った膨張」が起きる

最近の AI は、指示とまったく違う行動や、ハルシネーションによる暴走が減ったと感じる。一方で、直前の AI の判断を根拠に次の設計を重ね、当初の目的から離れていくことがある。例えば、当初の要件が「可用性は最小限でよく、異常時はエラーを報告して止まる」だったとする。それが実装中に、次のように膨張する。

- 機能 A を追加する
- ベストプラクティスとして自動復旧を追加する
- 復旧できない場合のフェイルセーフを追加する

普通のオーバーエンジニアリングは「早すぎた作り込み」という時間軸で捉えられることが多い。それに対して、AI では「目的を見失った膨張」が多いように思う。

Goal Context に「自己復旧を増やさず停止する」と書かれていれば、別の AI による目的レビューで、過剰な自己復旧実装が指摘される可能性を期待できる。手動でも効果があり、自動化するとさらに楽になる。

## 目的レビューと修正を最大3回まで自動化する

自動版では、専用 Skill を指定してゴール文書を渡すと、目的レビューと指摘された箇所の修正を最大3回まで繰り返す。「最大3回」は、ここで紹介する自動レビューの性質だ。

事前準備として、まずレビュー用エージェントを持つアプリをインストールする。

https://github.com/suusanex/coding_agent_plan_and_verify_process/blob/main/apps/PurposeReviewRunner/README.md

次に、専用 Skill を apm などで導入する。

https://github.com/suusanex/coding_agent_plan_and_verify_process/blob/main/apm-packages/persistent-purpose-review/README.md

準備後は、実行時に次のように依頼する。

> SKILL persistent-purpose-review を実行して。レビューのコンテキストは issue https://github.com/suusanex/blog_draft_webapp/issues/3 をそのまま渡して

「Skill を指定するだけ」と言うには事前準備が面倒ではある。それでも、毎回手動でレビュー依頼を繰り返すよりは楽になった。

ゴールを書いたドキュメントや Issue をもとに AI へプランから実装まで任せる場面で、実装がゴールを満たしていない問題をレビューで減らしたい。多くのコーディング場面で使える。

PR 作成後、別の AI へゴール文書と PR の URL を渡し、「この PR が目的を満たしているかレビューして」と依頼する。経過を知るコーディングエージェント自身ではなく、別エージェントにゴールと PR だけを見せることで、途中の誤解に引きずられにくくする。仕様書には従っていても当初のゴールを実現していないパターンを検出したい。

実績として、このレビューを通過したものはたいていそのまま疎通する。一般的な保証ではない。

背景: 最近の AI は指示と全く違う行動やハルシネーションによる暴走は減ったと感じる一方、直前の AI の判断を根拠に次の設計を重ね、当初の目的から離れる。例えば「可用性は最小限でよく、異常時はエラーを報告して止まる」が、「機能A追加 → ベストプラクティスとして自動復旧 → 復旧できない場合のフェイルセーフ追加」へ膨張する。

普通のオーバーエンジニアリングを「早すぎた作り込み」という時間軸で捉えるのに対し、AI では「目的を見失った膨張」が多いように思う。Goal Context に自己復旧を増やさず停止すると書かれていれば、過剰な自己復旧実装がレビューで指摘される可能性を期待できる。手動でも効果があり、自動化でさらに楽になる。

自動版は、Skill を指定してゴール文書を渡すと目的レビューと指摘修正を最大 3 回まで繰り返すものとして紹介する。事前準備と実行時の操作を混同しない。

- レビュー用エージェントを持つアプリを事前にインストールする: https://github.com/suusanex/coding_agent_plan_and_verify_process/blob/main/apps/PurposeReviewRunner/README.md
- 専用 Skill を apm などで導入する: https://github.com/suusanex/coding_agent_plan_and_verify_process/blob/main/apm-packages/persistent-purpose-review/README.md
- 実行時の例: 「SKILL persistent-purpose-review を実行して。レビューのコンテキストは issue https://github.com/suusanex/blog_draft_webapp/issues/3 をそのまま渡して」

「最大 3 回」は紹介対象の自動レビューの性質。「指定するだけ」と言うには準備が面倒だが、毎回手動でレビュー依頼を繰り返すより楽、という留保もある。
